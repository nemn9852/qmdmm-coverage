26 /**
27 * @class Logic
28 * @ingroup QMdmmCore
29 * @brief The MDMM Game logic.
30 *
31 * This is the place where logic is run.
32 * The logic is basically a state machine, where the states are changed based on the game process.
33 *
34 * A typical MDMM game run is like following: (ref. @c Logic::State)
35 *
36 * <table>
37 * <thead>
38 * <tr>
39 * <th>State
40 * <th>Definition
41 * <th>Accepted Slots
42 * <th>Notes
43 * </tr>
44 * </thead>
45 * <tbody>
46 * <tr>
47 * <td>@c Logic::BeforeRoundStart
48 * <td>The game / round has not yet started yet. Typically due to waiting for preparation of agents.
49 * <td>@c Logic::addPlayer() @c Logic::removePlayer() @c Logic::roundStart()
50 * <td>When @c Logic::addPlayer() or @c Logic::removePlayer() is called, all the upgrades are cleared.
51 * </tr>
52 * <tr>
53 * <td>@c Logic::RpsForAction
54 * <td>Rock-Paper-Scissors is requested for actions. This is always the first request per action time.
55 * <td>@c Logic::rpsReply()
56 * <td>@c Logic::requestRpsForAction() is emitted when this state enters, @c Logic::rpsResult() is emitted when this state exits to report the result.<br />
57 * If result is a tie @c Logic::RpsForAction re-enters. The number of retries is
58 * not bounded and no deterministic fallback follows a given number of them: a tie
59 * is inherent to Rock-Paper-Scissors, so capping the retries would not make it any
60 * less likely. Consequently, if all alive players keep answering with the same
61 * throw, this state is never left (known limitation).<br />
62 * If there is only one winner, he / she gets all the action orders and @c Logic::Action enters.<br />
63 * Else @c Logic::ActionOrder enters.
64 * </tr>
65 * <tr>
66 * <td>@c Logic::ActionOrder
67 * <td>If multiple winners has determined in the @c Logic::RpsForAction state, then in this action time the winners should determine the action order.
68 * <td>@c Logic::actionOrderReply()
69 * <td>@c Logic::requestActionOrder() is emitted when this state enters.<br />
70 * If multiple agents chose same action order, @c Logic::RpsForActionOrder enters.<br />
71 * Else the actions are got by the choosers, @c Logic::actionOrderResult() is emitted and @c Logic::Action enters.
72 * </tr>
73 * <tr>
74 * <td>@c Logic::RpsForActionOrder
75 * <td>If multiple winners chose same action order, request Rock-Paper-Scissors to determine who can actually get the action order.
76 * <td>@c Logic::rpsReply()
77 * <td>@c Logic::requestRpsForActionOrder() is emitted when this state enters, @c Logic::rpsResult() is emitted when this state exits to report the result.<br />
78 * If result is a tie @c Logic::RpsForActionOrder re-enters.<br />
79 * If the result is not a tie, but there are multiple winners, @c Logic::RpsForActionOrder re-enters with only winners are requested.<br />
80 * Else the action order is got by the winner. Then if there are still undetermined action orders, @c Logic::ActionOrder enters, else @c Logic::actionOrderResult() is emitted and @c Logic::Action enters.
81 * </tr>
82 * <tr>
83 * <td>@c Logic::Action
84 * <td>Request action then apply the action.
85 * <td>@c Logic::actionReply()
86 * <td>When a player die due to an action before his action order, then his action is skipped.<br />
87 * @c Logic::requestAction() is emitted when this state enters, @c Logic::actionResult() is emitted then action is applied when this state exits.<br />
88 * If there is less than 1 player alive after an action, the remained actions are discarded, @c Logic::roundOver() is emitted and round overs.<br />
89 * </tr>
90 * <tr>
91 * <td>@c Logic::Upgrade
92 * <td>Request upgrade then apply the upgrade.
93 * <td>@c Logic::upgradeReply()
94 * <td>@c Logic::requestUpgrade() is emitted when this state enters, @c Logic::upgradeResult() is emitted when this state exits to report the result.<br />
95 * When all upgradable properties reaches maximum value, @c Logic::gameOver() is emitted and game overs.
96 * </tr>
97 * </tbody>
98 * </table>
99 *
100 * @note The Logic is a synchronous, reply-driven state machine: each
101 * @c requestXxx signal expects a matching @c xxxReply() slot call, and that
102 * reply advances the state machine (possibly emitting further requests) within
103 * the same call stack. Some requests are emitted in a loop over players -- for
104 * example @c requestUpgrade() is emitted once per player with upgrade points --
105 * so a directly-connected slot replies re-entrantly while the loop is still
106 * running. This is safe by design: each phase only advances once every
107 * expected reply has been collected (the reply handlers count replies and act
108 * only when the set is complete), and the emit loops iterate over stable
109 * containers that the re-entrant advance does not mutate. A direct connection
110 * in a single-threaded setup is therefore equivalent to a queued connection;
111 * no particular connection type is required. (The reference implementation in
112 * QMdmmNetworking runs Logic on its own thread with queued connections purely
113 * for thread marshaling, not because direct connection is unsafe.)
114 */
