27 * @class Logic
28 * @brief The MDMM Game logic.
29 *
30 * This is the place where logic is run.
31 * The logic is basically a state machine, where the states are changed based on the game process.
32 *
33 * A typical MDMM game run is like following: (ref. @c Logic::State)
34 *
35 * <table>
36 * <thead>
37 * <tr>
38 * <th>State
39 * <th>Definition
40 * <th>Accepted Slots
41 * <th>Notes
42 * </tr>
43 * </thead>
44 * <tbody>
45 * <tr>
46 * <td>@c Logic::BeforeRoundStart
47 * <td>The game / round has not yet started yet. Typically due to waiting for preparation of agents.
48 * <td>@c Logic::addPlayer() @c Logic::removePlayer() @c Logic::roundStart()
49 * <td>When @c Logic::addPlayer() or @c Logic::removePlayer() is called, all the upgrades are cleared.
50 * </tr>
51 * <tr>
52 * <td>@c Logic::RpsForAction
53 * <td>Rock-Paper-Scissors is requested for actions. This is always the first request per action time.
54 * <td>@c Logic::rpsReply()
55 * <td>@c Logic::requestRpsForAction() is emitted when this state enters, @c Logic::rpsResult() is emitted when this state exits to report the result.<br />
56 * If result is a tie @c Logic::RpsForAction re-enters.<br />
57 * If there is only one winner, he / she gets all the action orders and @c Logic::Action enters.<br />
58 * Else @c Logic::ActionOrder enters.
59 * </tr>
60 * <tr>
61 * <td>@c Logic::ActionOrder
62 * <td>If multiple winners has determined in the @c Logic::RpsForAction state, then in this action time the winners should determine the action order.
63 * <td>@c Logic::actionOrderReply()
64 * <td>@c Logic::requestActionOrder() is emitted when this state enters.<br />
65 * If multiple agents chose same action order, @c Logic::RpsForActionOrder enters.<br />
66 * Else the actions are got by the choosers, @c Logic::actionOrderResult() is emitted and @c Logic::Action enters.
67 * </tr>
68 * <tr>
69 * <td>@c Logic::RpsForActionOrder
70 * <td>If multiple winners chose same action order, request Rock-Paper-Scissors to determine who can actually get the action order.
71 * <td>@c Logic::rpsReply()
72 * <td>@c Logic::requestRpsForActionOrder() is emitted when this state enters, @c Logic::rpsResult() is emitted when this state exits to report the result.<br />
73 * If result is a tie @c Logic::RpsForActionOrder re-enters.<br />
74 * If the result is not a tie, but there are multiple winners, @c Logic::RpsForActionOrder re-enters with only winners are requested.<br />
75 * Else the action order is got by the winner. Then if there are still undetermined action orders, @c Logic::ActionOrder enters, else @c Logic::actionOrderResult() is emitted and @c Logic::Action enters.
76 * </tr>
77 * <tr>
78 * <td>@c Logic::Action
79 * <td>Request action then apply the action.
80 * <td>@c Logic::actionReply()
81 * <td>When a player die due to an action before his action order, then his action is skipped.<br />
82 * @c Logic::requestAction() is emitted when this state enters, @c Logic::actionResult() is emitted then action is applied when this state exits.<br />
83 * If there is less than 1 player alive after an action, the remained actions are discarded, @c Logic::roundOver() is emitted and round overs.<br />
84 * </tr>
85 * <tr>
86 * <td>@c Logic::Upgrade
87 * <td>Request upgrade then apply the upgrade.
88 * <td>@c Logic::upgradeReply()
89 * <td>@c Logic::requestUpgrade() is emitted when this state enters, @c Logic::upgradeResult() is emitted when this state exits to report the result.<br />
90 * When all upgradable properties reaches maximum value, @c Logic::gameOver() is emitted and game overs.
91 * </tr>
92 * </tbody>
93 * </table>
94 *
95 * @note The Logic is a synchronous, reply-driven state machine: each
96 * @c requestXxx signal expects a matching @c xxxReply() slot call, and that
97 * reply advances the state machine (possibly emitting further requests) within
98 * the same call stack. Some requests are emitted in a loop over players — for
99 * example @c requestUpgrade() is emitted once per player with upgrade points —
100 * so a directly-connected slot replies re-entrantly while the loop is still
101 * running. This is safe by design: each phase only advances once every
102 * expected reply has been collected (the reply handlers count replies and act
103 * only when the set is complete), and the emit loops iterate over stable
104 * containers that the re-entrant advance does not mutate. A direct connection
105 * in a single-threaded setup is therefore equivalent to a queued connection;
106 * no particular connection type is required. (The reference implementation in
107 * QMdmmNetworking runs Logic on its own thread with queued connections purely
108 * for thread marshaling, not because direct connection is unsafe.)
